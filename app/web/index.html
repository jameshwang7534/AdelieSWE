SPECIALISTS, WITH SHARED CONTEXT

Five roles. One coordinated change.

01 / PLAN

Planner

Turns the issue and retrieved code into small tasks with explicit dependencies.

02 / BUILD

Coding

Proposes focused patches, validates paths, and applies changes in a task workspace.

03 / CHECK

Test

Selects trusted commands using deterministic policy and runs them through Docker.

04 / REPAIR

Debug

Uses test failures and previous attempts to propose a fix, within a hard retry limit.

05 / REVIEW

Review

Checks the full diff against the issue. Blocking findings prevent publication.

MAKE YOUR FIRST RUN SMALL

Start with one issue.
Learn from the whole journey.

1. Start the local services

Use Python 3.12. Start PostgreSQL and Redis, apply migrations, then run FastAPI, a Celery worker, and one Beat scheduler. Run these commands from the repository root in an activated virtual environment.

docker compose up -d --wait
python -m alembic upgrade head
python -m uvicorn app.main:create_app --factory

2. Configure and submit

Keep GitHub and model credentials in your local .env. Configure a structured-output LLM and a 1536-dimensional embedding model. Create a small GitHub issue, then submit it in the API explorer.

How do I start the background workers?

Keep each command running in a separate activated terminal at the repository root. These are Windows development commands. Run only one Beat scheduler. Pre-pull the trusted test image before executing code.

docker pull python:3.12-slim

python -m celery -A app.workers.celery_app:app worker --pool=solo --concurrency=1 -Q orchestration,indexing,agents --loglevel=INFO

python -m celery -A app.workers.celery_app:app beat --loglevel=INFO
What do I send to POST /workflows?

Replace the placeholders and use an existing issue number. Generate a new request ID with [guid]::NewGuid().ToString() in PowerShell. Reuse that ID and payload when retrying the same submission.

{
  "request_id": "YOUR-NEW-UUID",
  "github_owner": "YOUR-GITHUB-OWNER",
  "github_name": "YOUR-TEST-REPOSITORY",
  "issue_number": 1,
  "publish_pull_request": false
}

Follow progress with GET /workflows/{id}. Enable publication on the initial request only when you want a real remote branch and PR. There is no automatic merge.

How do I know it is working?

GET /health checks FastAPI. GET /ready checks PostgreSQL and Redis. POST /tasks/ping and GET /tasks/{id} test the worker path. These do not verify provider credentials. Workflow status includes stage, attempts, errors, and generated IDs.

What are the current limits?

This is a development platform. Automated acceptance uses fake GitHub and model providers with real local infrastructure. Real-provider end-to-end integration has not yet been certified. Scale measurements cover a synthetic 5,000-file repository, not arbitrary production workloads. API authentication is not implemented: keep the app on localhost. Docker isolation reduces risk but is not a guarantee for hostile code. Review every generated change.
